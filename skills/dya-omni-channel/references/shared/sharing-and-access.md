The minimum needed to avoid writing code that leaks data or throws for ordinary users. This is the
shape of the model, not the whole of it — `dya-permissions` is the skill that owns the subject and
covers the layers, the edge cases and the design guidance.

## Two independent axes

Salesforce answers two separate questions, and a user needs a "yes" on both to act on a record.

```text
WHICH RECORDS can this user see?          WHAT can they do with an object and its fields?
- Org-Wide Defaults (the floor)           - Object permissions: Create/Read/Edit/Delete
- Role hierarchy                          - Field-Level Security, per field
- Sharing rules                           - View All / Modify All
- Manual and Apex sharing                 - Granted by profile + permission sets
- Teams, implicit sharing
```

The most common bug is satisfying one axis and not the other. "The record is shared with them but
they still cannot edit it" is missing object or field permissions. "They have Edit on the object but
see no rows" is missing sharing.

## Where permissions come from

Every user has exactly one **profile** and any number of **permission sets**. Permissions are
**additive**: the user gets the union of everything granted, and there is no "deny" — you cannot take
a permission away by adding another set. **Permission set groups** bundle sets for a job function,
and **muting** inside a group is the one mechanism that subtracts.

Profiles are not being removed, but new capability lands in permission sets. Assign through permission
sets; leave the profile minimal.

## System mode versus user mode

Apex can run with permissions enforced or bypassed. This is the single most important thing to get
right in code.

| Context | Access mode | Sharing enforced? |
|---|---|---|
| Trigger | System mode, always, in every API version | No |
| Class stamped API 67.0 or above | SOQL, SOSL and DML default to `USER_MODE` | Per the sharing keyword |
| Class stamped below 67.0 | System mode by default | Per the sharing keyword |
| Anonymous Apex | Runs as the executing user | Yes |
| Flow (default) | System mode with sharing, unless set to user context | Depends on the setting |

From API 67.0 a class with no `with sharing` / `without sharing` keyword defaults to `with sharing`.
Write the keyword explicitly anyway — the reader should not have to know the version to know the
behaviour.

```apex
public with sharing class AccountService {
    public static List<Account> forUser(Set<Id> ids) {
        // Object and field permissions plus sharing are enforced.
        return [SELECT Id, Name FROM Account WHERE Id IN :ids WITH USER_MODE];
    }
}
```

`WITH SECURITY_ENFORCED` was removed at 67.0 and no longer compiles. Where a partial result is
acceptable, `Security.stripInaccessible` removes fields the user cannot see instead of throwing.

## Record types

A **record type** selects which picklist values and which page layout apply to a record, and is a
common source of "the value is valid in the org but rejected on save". Access to a record type is
granted through the profile or permission set, separately from field permissions.

## Guest users

Public sites and Experience Cloud sites run as a **guest user** with a dedicated, deliberately
crippled profile: no role, read-only sharing rules of their own kind, and no access to most objects
by default. Code reachable by a guest is code reachable by the internet. Never rely on the guest
profile being restrictive by accident — check what it actually grants.

## Anti-Patterns

| Anti-Pattern | Correct Approach |
|---|---|
| Omitting the sharing keyword and relying on the default | State `with sharing` or `without sharing` explicitly |
| `without sharing` to make a bug go away | Find which layer is missing; bypass only where genuinely required and comment why |
| Assuming a trigger honours sharing | Triggers are system mode; filter explicitly for user-behalf work |
| Granting Modify All Data to close a sharing gap | Targeted sharing plus View All / Modify All on the one object |
| Testing only as an administrator | Test as a user with the real permission set, using `System.runAs` |
| Permissions on the profile | Permission sets and permission set groups |
