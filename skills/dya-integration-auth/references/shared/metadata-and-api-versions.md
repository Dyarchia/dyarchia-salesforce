This is the single source of truth for API version numbers, retirement status and version semantics
across the library. Where a skill needs one of these facts it points here rather than restating it,
because a restated date is a date that goes stale silently.

## Two different things are called "the API version"

**The version stamped on a piece of metadata.** Every Apex class, trigger, LWC, Aura component and
Visualforce page carries its own `apiVersion` in its `-meta.xml`. It decides which language and
runtime semantics that artefact gets — including the security defaults described in
`platform-deltas.md`. It does **not** change when the org is upgraded. Raising it is an explicit edit
plus a redeploy, and it is a behavioural change that needs testing.

```xml
<!-- MyClass.cls-meta.xml -->
<?xml version="1.0" encoding="UTF-8"?>
<ApexClass xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>68.0</apiVersion>
    <status>Active</status>
</ApexClass>
```

**The version in a REST or SOAP endpoint URL.** `/services/data/v68.0/sobjects/Account` — the
contract an external caller asks for. This is what Salesforce retires. Winter '27 adds a `/latest`
alias that resolves to the newest version; it is convenient for exploration and a poor choice in
production, because the integration's behaviour then changes three times a year without a deploy.

## Retirement status

Retiring an endpoint version means calls to it **stop working**, returning `410 GONE` or a SOAP
fault. It affects the `vXX.X` in standard endpoint URLs only.

| Versions | Status |
|---|---|
| 7.0 – 20.0 | Retired |
| 21.0 – 30.0 | Retired |
| 31.0 – 40.0 | Deprecated and scheduled for retirement — build nothing new on them |
| 41.0 and above | Supported |

Retirement of an endpoint version does **not** retire your custom Apex REST or SOAP web services,
Apex classes, triggers, Flows or Visualforce pages. Those keep running under their own stamped
version. What breaks is an external caller addressing a retired `/services/data/vXX.X/` path.

SOAP `login()` is a separate, narrower retirement: it is already unavailable in 65.0 and above, and
is on its way out for 31.0–64.0. It now also requires the **Any API Auth** user permission, enforced
by default in new orgs. See `dya-integration-auth`.

## Targets

- **New integrations**: the current version, 68.0.
- **Existing integrations**: 41.0 is the hard floor. Anything below it is on borrowed time and should
  be flagged during review.
- **New Apex, LWC and Flow**: the current version. There is no reason to stamp new metadata lower.
- **Raising existing metadata**: deliberate, one artefact at a time, with tests re-run as a non-admin
  user. The security defaults at 67.0 are why this is not a bulk find-and-replace.

## Finding what you have

```bash
# Every Apex class below the floor, from a retrieved source tree.
grep -rl "<apiVersion>[1-3][0-9]\.0</apiVersion>" force-app/

# The org's own current version.
sf org display --target-org myorg --json
```

The Tooling API exposes `ApexClass.ApiVersion` for a query-based audit across an org you cannot
retrieve in full.
