Salesforce runs many customers on shared infrastructure, so it caps what any single execution may
consume. Exceed a cap and the runtime throws a `System.LimitException` that **cannot be caught and
recovered from** — the transaction rolls back. This is why "bulkify everything" is a rule rather
than a preference: code written one-record-at-a-time works in a unit test and fails the moment a
user imports 200 rows.

## The transaction

A **transaction** is one synchronous unit of execution: a trigger and everything it cascades into, a
single Apex REST call, one Queueable's `execute`. Limits are counted per transaction and reset when
it ends. Calling a second class does not reset anything — the whole call tree shares one budget.

## The limits that decide designs

| Limit | Synchronous | Asynchronous |
|---|---|---|
| SOQL queries issued | 100 | 200 |
| Rows retrieved by SOQL | 50,000 | 50,000 |
| SOSL searches | 20 | 20 |
| DML statements (`insert`, `update`, `delete`, …) | 150 | 150 |
| Rows processed by DML | 10,000 | 10,000 |
| CPU time | 10,000 ms | 60,000 ms |
| Heap size | **10 MB** | **25 MB** |
| Callouts per transaction | 100 | 100 |
| Cumulative callout timeout | 120 s | 120 s |
| `@future` invocations | 50 | 0 from a batch/future |
| Queueable jobs enqueued | 50 | 1 (chaining) |
| Rows from `Database.getQueryLocator` | 10,000 | 10,000 |
| `sendEmail` invocations | 10 | 10 |

Heap rose in Winter '27 from 6 MB / 12 MB. An org setting can hold the old value during transition,
so do not assume the new ceiling in code that must run everywhere.

Async contexts (`@future`, Queueable, Batch, Schedulable) get the higher CPU and heap budgets. That
is the main reason to move work async — not merely "it takes a while".

Verify any number you are about to write into a customer's design against the current *Execution
Governors and Limits* table in the Apex Developer Guide. The values above are the ones that shape
architecture and change rarely; the long tail changes more often.

## What the numbers imply

- **100 SOQL and 150 DML per transaction** is why queries and DML go outside loops. One trigger
  firing on a 200-record batch that queries per record burns 200 of a 100-query budget.
- **50,000 rows retrieved** is why unbounded `SELECT` is unsafe. Filter, or use a batch/cursor.
- **10,000 ms CPU** is the limit most often hit by nested loops over collections. Build a `Map` keyed
  on the join field instead of scanning an inner list.
- **10 MB heap** is why you stream rather than materialise. `for (Account a : [SELECT …])` chunks
  internally; `List<Account> all = [SELECT …]` does not.
- **100 callouts, 120 s cumulative** is why external calls are batched or moved to an event.

## Checking limits at runtime

```apex
if (Limits.getQueries() > Limits.getLimitQueries() - 10) {
    // Defer the rest rather than dying mid-transaction.
}
System.debug(Limits.getCpuTime() + ' of ' + Limits.getLimitCpuTime());
```

Every limit has a `Limits.getX()` / `Limits.getLimitX()` pair. Use them to fail gracefully in
framework code, not as a substitute for bulkification.

## Two things that are not governor limits

- **Org-wide daily allocations** — API calls per 24 hours, Flow interviews per month, async Apex
  executions per day. These are billing-scale quotas, not per-transaction caps, and are visible under
  Setup › Company Information.
- **Row locking.** `UNABLE_TO_LOCK_ROW` means another transaction held a lock on the same record —
  commonly the shared parent when many children are inserted at once. The fix is ordering and batch
  size, not a bigger limit.

## Anti-Patterns

| Anti-Pattern | Correct Approach |
|---|---|
| SOQL or DML inside a `for` loop | Query once into a `Map`, collect into a `List`, DML once after the loop |
| `List<SObject> all = [SELECT … ]` with no filter | Filter on an indexed field, or iterate the query directly |
| Nested loops over two collections | Build a `Map` keyed on the join field |
| Callout inside a loop | Aggregate the payload, or publish an event and call once |
| Assuming a test with one record proves bulk safety | Test with 200+ records — that is what the platform will send |
| Catching `LimitException` to "handle" it | It is not recoverable; design under the limit instead |
