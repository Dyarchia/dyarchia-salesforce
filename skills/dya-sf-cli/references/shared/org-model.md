Where Salesforce code lives, how it gets there, and the vocabulary the rest of the library assumes.
`dya-sf-cli` is the command catalogue; this is the mental model behind it.

## An org is the unit of everything

An **org** is a single tenant: its own data, its own configuration, its own users, its own copy of
every customisation. There is no "server" to deploy to and no filesystem to inspect. Code is
**metadata**, and it moves between orgs as metadata.

| Org type | What it is | Lives for |
|---|---|---|
| Production | The live org. Real users, real data | Indefinitely |
| Sandbox | A copy of production. Developer, Developer Pro, Partial Copy, Full | Until refreshed or deleted |
| Scratch org | A disposable org built from a config file and a source push | Up to 30 days |
| Developer Edition | A free permanent org for learning and packaging | Indefinitely |

Sandboxes get the next release **ahead of production** during preview windows, which is where a new
API version is tested before it reaches live users.

## Metadata and the source tree

The local repository holds **source-format metadata**: one file (plus a `-meta.xml` sidecar) per
artefact, under `force-app/main/default/` by convention.

```text
force-app/main/default/
├── classes/          MyService.cls + MyService.cls-meta.xml
├── triggers/         AccountTrigger.trigger + .trigger-meta.xml
├── lwc/myCmp/        myCmp.js, myCmp.html, myCmp.js-meta.xml
├── objects/          custom objects, fields, list views, record types
├── flows/            Flow definitions
└── permissionsets/   permission sets
```

A **DX project** is any directory containing an `sfdx-project.json` that names those package
directories. That file is what makes `sf` commands work in a folder.

## Getting code in and out

```bash
sf project deploy start --source-dir force-app --target-org myorg   # local → org
sf project retrieve start --metadata ApexClass --target-org myorg   # org → local
sf org login web --alias myorg                                      # authorise an org
sf apex run test --target-org myorg --code-coverage                 # run tests
```

Deploying to **production** runs Apex tests and requires **75% aggregate Apex code coverage**, with
every trigger covered by at least one line. Sandboxes do not enforce that gate, which is why coverage
problems surface late. Declarative Flow tests do **not** contribute to this percentage.

Two orgs must be on **the same API version** for certain metadata types to deploy between them —
Agentforce agent definitions in 68.0 are the current example.

## Packaging

- **Unlocked packages** — versioned bundles of your own metadata, the modern way to modularise an org.
- **Managed packages** — what ISVs publish on AppExchange. Their internals are hidden, their
  components carry a **namespace prefix** (`acme__Field__c`), and you cannot edit them.
- **Change sets** — the point-and-click path between related orgs. Slow, unversioned, no diff. Fine
  for a one-off, wrong as a delivery process.

A **namespace** matters in code: in a subscriber org, a packaged field is addressed with its prefix,
and Winter '27 adds `explicitNamespace` on `Database.QueryOptions` so a subscriber's own field of the
same name cannot shadow the packaged one.

## Anti-Patterns

| Anti-Pattern | Correct Approach |
|---|---|
| Editing metadata directly in production | Change in a sandbox or scratch org, deploy the source |
| Change sets as the standing release process | Source-tracked deploys from version control |
| Discovering coverage below 75% at deploy time | Run tests with coverage against a sandbox first |
| Assuming a sandbox and production are on the same release | Check during preview windows; they diverge on purpose |
| Hardcoding record IDs that differ per org | Custom metadata, custom settings, or a query by name |
