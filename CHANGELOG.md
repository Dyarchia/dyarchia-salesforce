## [Unreleased]

### Added

- **`dist/dyarchia-salesforce.plugin` — the library imports into Claude Desktop.** It would not before, and the reason was structural rather than a bug: Desktop accepts only `.zip` and `.plugin` extensions and requires a `.claude-plugin/plugin.json` at the archive root or a `SKILL.md` at the root. A `.skill` bundle has neither — it is rooted at `<skill-name>/` and carries no manifest — so importing one fails with *"The archive must contain a .claude-plugin/plugin.json manifest, or a top-level SKILL.md"*, and renaming the extension does not help because the shape is wrong rather than the label. New `scripts/build-plugin` twins pack `.claude-plugin/`, `.codex-plugin/`, `skills/`, `README.md` and `LICENSE` into one archive carrying all twenty-six skills, deliberately omitting `references-shared/` (already materialised into each skill), `scripts/`, `dist/` and `docs/`. Reproducible on the same terms as the skill bundles — sorted entries, fixed 1980-01-01 timestamps, forward slashes — and verified byte-identical across two builds. One caveat is documented in both contract files because nothing enforces it: **`validate-skills` does not check this archive**, since it only looks up `dist/<name>.skill` per skill, so it has to be rebuilt in the same commit as any change to `skills/` or a manifest.

- **`.codex-plugin/plugin.json` — the library installs on Codex and ChatGPT.** The skills were never Claude-specific: each is a folder with a `SKILL.md` carrying `name` and `description` in frontmatter, which is the Agent Skills shape Codex, Grok and Mistral Vibe all read. Only the manifest differed, and Codex expects exactly the layout this repo already had — a manifest beside a `skills/` tree — so support is one six-line file pointing at the same content. **Grok needs nothing at all**: it reads Claude Code marketplaces, plugins, skills, MCP servers, agents, hooks and `CLAUDE.md` with no configuration. The README gains an "Install on other agents" section covering both, plus Mistral Vibe and the vendor-neutral `.agents/skills/` discovery path. The frontmatter contract turns out to be load-bearing for a reason nobody planned: **exactly two keys is the intersection every host requires**, and hosts ignore keys they do not know, so the contract was already portable. A second manifest duplicates the plugin name, version and description, which is precisely the drift this repo exists to prevent — so `validate-skills` checks both manifests against each other and against `skills/`, and pins the Codex `skills` path to the source root, because changing `SourceRoot` without it would break the Codex install silently.

- **`validate-skills` now checks the stated skill count.** The count is asserted in prose in several places, and one of them — `plugin.json`'s description — went stale unnoticed when `dya-omni-channel` made it twenty-six, surviving a clean validation run because the existing check reads that description for the *platform version* only. Five sites are now verified against the number of folders under `skills/` and **fail** on disagreement: the README catalogue line, both boxes of the README layout diagram, the README install line, and the plugin description. The count therefore lands everywhere or the build stops, exactly like the platform version. Rewording an assertion so no number survives produces a **warning** rather than silence, because a check that quietly stops applying is worse than one that fails. Verified in both twins by perturbing each of the five sites in turn and by removing an assertion entirely; the prose counts in `CLAUDE.md` and `CONTRIBUTING.md` remain manual and are flagged as such.

## [0.4.0] - 2026-09-09

The first release cut since `0.1.0`. The `0.2.0` and `0.3.0` version numbers were carried in the

### Added

- **`validate-skills` now checks the routing graph.** Skills hand off to each other by naming a sibling in backticks, and that graph is what lets a reader start anywhere in the library. It was the one contract nothing verified: renaming or removing a skill left every prose mention of the old name pointing at nothing, silently, and `CONTRIBUTING.md` could only advise grepping for them by hand. Both script twins now scan every `.md` under a skill — excluding `references/shared/`, which is generated — and **fail** on a backticked `dya-<name>` with no matching folder, naming the file each dangling reference sits in. It reads the graph already present in the prose rather than asking for it a second time in frontmatter, so adding a handoff still costs nothing beyond writing the sentence. The existing `$nonSkillTokens` / `NON_SKILL_TOKENS` allowlist covers this check too. The tree passes today: all twenty-six skills cite only names that resolve.

- **`dya-omni-channel`** — Service Cloud routing, the library's twenty-sixth skill and the last structural gap in it. Nothing among the previous twenty-five had a Service Cloud footprint: a full-text search for Omni-Channel, `ServiceChannel`, `AgentWork` or `PendingServiceRouting` returned nothing. `dya-agentforce` covers designing the agent and stops exactly where a conversation needs a person, which is where this skill starts. It carries the routing chain end to end — work item → `ServiceChannel` → queue and `QueueSobject` → `QueueRoutingConfig` → `PendingServiceRouting` → `AgentWork`, with `ServicePresenceStatus` and `PresenceUserConfig` on the agent's side — as an ordered diagnostic list, because every "it is not routing" question is a position on it. The `routeWork` Flow action gets its own section as **the seam with Agentforce, in both directions**: `queueId` escalates from an agent to a person, and `agentforceEmployeeAgentId` or `digitalWorkerId` delegates the other way, so an agent is not a terminal node. Three references carry the detail — the data model, the deploy and query traps (`ServiceChannel.Metadata` is not Tooling-SOQL-queryable while `WorkSkillRouting.Metadata` is, and the v66 renames where `capacityWeight` was **replaced** rather than moved, with per-agent totals now on `PresenceUserConfig.Capacity`), and the `routeWork` targets with the flow-type and error taxonomy where a **404 means the flow is not activated** rather than absent. The one that costs the most time is in the body: with `enableOmniChannel` off, every downstream type rejects with `INVALID_TYPE` naming the type you deployed and never mentioning the setting.

- **`CONTRIBUTING.md`** — the authoring procedure now lives at the repository root, written for a contributor to read rather than for an assistant to load. It carries what the repo-local `dya-skill-authoring` skill carried: the artifacts that must agree, the branch and pull-request flow, adding, editing, splitting and removing a skill, the full validator check table, the commit conventions, and the anti-patterns.

### Changed

- **The marketplace is renamed from `dyarchia` to `dyarchia-salesforce`.** The plugin already carried the right name; the marketplace was named after the organisation rather than this repository. Since every Dyarchia domain ships as its own repo serving its own marketplace, each sibling would have declared a marketplace called `dyarchia` and a consumer adding two of them would have collided. The install line becomes `/plugin install dyarchia-salesforce@dyarchia-salesforce`, where the part after the `@` is the marketplace — **anyone who already added the marketplace under the old name has to re-add it.** `CLAUDE.md` gains the rule this came from: name a domain repo's marketplace after the repo, never after the org.

- **`plugin.json`'s description said "25 domain playbooks" after `dya-omni-channel` made it twenty-six.** The validator checks that description for the platform version but not for the skill count, so the drift passed a clean run. Corrected, and both `CLAUDE.md` and `CONTRIBUTING.md` now name the description as the one place the count can go stale without anything failing.

- **Publishing to `master` is now a fast-forward rather than a merge.** The old sync merged `develop` into `master`, which left a commit on `master` that never flowed back — so the counter grew by one per release and GitHub reported `develop` as **eight commits behind `master` while the two were byte-identical**. That is worse than cosmetic: the "behind" banner invites a `git merge master` on `develop`, which drags publish-only commits into the working branch and breaks the one-way flow the contract depends on. A single reconciling merge makes `master` an ancestor of `develop`, and from here `git push origin develop:master` fast-forwards, so the two share one history and cannot diverge again. Publishes are marked with an annotated tag instead — what a release marker is actually for, and it does not distort the branch graph. Documented in both `CLAUDE.md` and `CONTRIBUTING.md`, including that `master` lagging `develop` between publishes is the normal state, and that `master` is never force-pushed.

- **`dya-omnistudio` gains deployment and the `PropertySetConfig` keys.** The skill covered building OmniStudio artifacts and said nothing about moving them, which is a gap with consequences: **OmniStudio artifacts are records, not metadata**, so they do not travel with `sf project deploy` at all. A new §4b and `references/datapacks.md` cover the `vlocity` Build tool, the fixed command order (`validateLocalData` → `packGetDiffs` → `packDeploy` → `packRetry` repeatedly while the error count drops, because dependency ordering resolves across passes), incremental `gitCheck` deploys, and the error-to-cause table — where the root cause under most failures is **GlobalKey identity disagreeing between source and target** rather than the artifact being wrong. `references/ips-and-datamappers.md` gains the `PropertySetConfig` key inventory per element type and the **`%ElementName:fieldName%` merge syntax**, which is the actual mechanism behind everything the skill described abstractly as mapping a response node — along with the reason renaming an element breaks every downstream reference, and the distinction between `useQueueableApexRemoting` and `useFuture`, the latter returning no value so nothing downstream can read its output. The Remote Action `Callable` contract is **deliberately untouched** pending verification in an org; see the note below.

- **`dya-lwr-sites` can now create a site, not only build inside one.** New `references/site-provisioning.md` covers the Connect API creation endpoints (plus the self-service and PRM variants), template discovery — the accepted `templateName` strings vary by org, so they are discovered rather than hardcoded — and the sequence a new site needs before anyone can reach it. That sequence is the point: a freshly created site is `UnderConstruction` with only its creator as a member and unpublished pages, **there is no Connect API to activate it** (`PATCH /connect/communities/<id>` returns 405), so activation is a Metadata API `Network.status` change and publication is `sf community publish`. It also records the login-path trap behind most "the site is broken" reports: an Aura site logs in at `…/<prefix>/login`, not at the bare prefix. In the body, §7 gains the `DigitalExperienceBundle` rule that an agent gets wrong on the first try — **never reach for FlexiPage tooling on an LWR site**, where it silently does nothing — and that a page needs both a `route` and a `view`. `references/guest-and-seo.md` gains the actual `sharingGuestRules` XML contract, where `<guestUser>` takes the guest user's `CommunityNickname` rather than the URL path prefix and `<includeHVUOwnedRecords>` is required.

- **`dya-data360` gains Data Custom Code, schema introspection and the ingestion decisions made before the first call.** `datacustomcode` appeared **nowhere in the twenty-five skills**; the Python SDK was a single table row. New `references/code-extensions.md` covers the CLI and SDK, the project shape, `read_dlo` / `write_to_dmo` with the write modes that differ by target, CPU sizing (the default is already `CPU_2XL`, two steps up, and compute is credit-metered), and three facts that cost an afternoon each: **Python 3.11 exactly**, Docker needed for deploy but not for a local run, and `--package-dir` pointing at `./payload` rather than the project root. Plus the one that surprises people — **a local `run` executes against real Data 360 data, with no fixture layer.** `references/query-api.md` gains the four SSOT introspection endpoints, which are how you resolve a unified DMO's real name rather than guessing it, along with the rule that table names must be double-quoted in Data 360 SQL. `references/ingestion-api.md` gains the decisions that cannot be changed later: the stream category and what each requires, the **`__c` → `_c` field-name transform** on the way into a DLO, the three-hop auth flow whose ingest step goes to the **tenant URL and not the instance URL**, and the fact that a `202` means accepted rather than queryable, with validation failures surfacing in the Problem Records DLO family.

- **`dya-lwc` gains the LWS rule catalogue, the missing adapter family, and accessibility tests.** New `references/lws-rules.md` collects the Lightning Web Security rules where ordinary JavaScript compiles, deploys and then behaves differently: assignment to `window` and friends is blocked while reads are fine, a **`Map` or `Set` does not survive an event payload, a `@wire` or a child-component boundary**, mutating an `@api`-received or wired object is rejected, `srcdoc` is blocked outright, and `URL.createObjectURL` is gated by MIME type — which is what bounds the `blob:` download pattern §8 already teaches, since an omitted MIME type is the blocked case and fails silently. The catalogue also flags `blob:` as a URL scheme; the reference explains why that rule is about untrusted URLs rather than a blob your own code just minted, so the existing guidance stands with the MIME constraint made explicit. Separately, **`lightning/uiListsApi` appeared nowhere in the library**, which meant §1's escalation ladder routed a list view to GraphQL or Apex when `getListRecordsByName` exists; `references/lds-patterns.md` now carries all four adapter modules, the `optionalFields`-versus-`fields` distinction that decides whether a wire errors or degrades for a user without FLS, and `updateRecord`'s second argument (`ifUnmodifiedSince` for conflict detection, and the assignment-rule flags that default to false). `references/graphql-patterns.md` gains semi-joins and anti-joins, `currentUser`, polymorphic fragments and the mutation input rules; `references/jest-testing.md` gains `@sa11y/jest`.

- **`dya-apex` gains static analysis and the 66→67 crossing checklist.** `code-analyzer`, `SFGE`, `ast-dump` and `RetireJS` returned **zero hits** across the whole skill; the only tooling mention was three lines on ApexGuru. New `references/static-analysis.md` covers the seven engines (not the three the CLI skill claimed), the selector grammar, and the failures that produce no error at all — **there is no `--format`** (the output file's extension picks it), **`--json` is rejected** by `code-analyzer run` specifically, a `code-analyzer.yml` outside the project root is never discovered, and a misspelled rule name inside it is ignored silently so the override just never applies. It also carries the PMD 7 trap where boolean attributes are always present on the node, so `@WithSharing = false()` works and both `'false'` and `not(@WithSharing)` do not. `references/testing-patterns.md` gains the version-crossing procedure, whose fourth step is the one that gets skipped: `System.runAs` is not enough on its own — the user it runs as needs a **permission set granting the CRUD and FLS the code requires**, or every user-mode query throws, and a test that passes as an administrator and fails under `runAs` is usually reporting that rather than a bug. §3 now states that `without sharing` suppresses record sharing only. To buy the bytes, the kill-switch's implementation detail moves to `references/trigger-framework.md`, which already carried it, and the SRP size thresholds land in `references/solid-principles.md`.

- **`dya-agentforce` gains the two things a script author actually needs: the lifecycle mechanics and the list of constructs that lie.** New `references/agent-lifecycle-metadata.md` covers the bundle as a **pair** of files whose names must all match, why **deploy is not publish** (a deploy stages the bundle and creates no runtime entity; `sf agent publish` builds the `Bot` / `BotVersion` / `GenAiPlannerBundle` graph), the trap where a version-suffixed bundle is read-only and **deploying it succeeds as a silent no-op**, the fact that `retrieve --metadata Agent:X` leaves the bundle behind, and the open-source AgentScript SDK that compiles and lints a `.agent` file **with no org at all**. New `references/agent-control-flow-pitfalls.md` collects what compiles and then misbehaves: a bare `@variables.X` inside a `|` block passes its **literal name** to the model rather than the value, indentation under `|` is prose and not scope, `available when` gates action *definitions* and not only transitions, `before_reasoning` re-runs on every self-transition and erases state set earlier in the same turn, and the `configured → available → invoked → executed → effected` ladder — because an agent saying it created the ticket establishes none of those. `references/agent-script.md` gains `else if` (and that `elif` is a syntax error), the `unsupported-nested-if` lint rule, subagent block ordering with `before_reasoning` / `after_reasoning`, the `developer_name`-must-match-directory constraint, and the employee-versus-service `agent_type` rules. `references/lifecycle-and-api.md` gains Agent Health Monitoring alerts, where **there is no `sf agent alert` subcommand** and thresholds are 0–1 ratios rather than percentages. To make room for the citations, §4's Apex class listing moves to `references/apex-actions.md`, which already carried it.

- **`dya-field-service` gains the policy model and the mobile data-capture surface.** Two new references. `fsl-policy-model.md` covers what a scheduling policy is actually made of — the two junction objects, the fact that **type is a RecordType and there is no `Type__c` field** on either `Service_Goal__c` or `Work_Rule__c`, the relevance-group rules (mutually exclusive, and an overlap on Service Resource Availability *throws* rather than resolving), the thirteen `FSL__` Booleans that trigger code actually reads on `ServiceAppointment`, and the optimizer's penalty arithmetic. That last one has a consequence worth stating outright: **ASAP weights 1 through 21 are all identical**, because they round to 0 and clamp to 1, so tuning inside that band does nothing. `mobile-data-capture.md` covers a surface the skill did not touch at all — `DataCaptureFlow` with its three mandatory input variables, deployment as a **Tooling JSON round-trip rather than XML**, the `runtime_service_fieldservice:dc*` component namespace, `DynamicDataCapture`, and the sharing trap that shows an empty Forms tab on the device while an administrator's SOQL returns rows, because the UI API enforces sharing and the app caches its snapshot at login. In the body: §3 gains the database-versus-Apex rule engine distinction and the ~20-candidate target, which is the actual latency lever behind `GetSlots`; §6 gains `ParentRecordId` being create-only and polymorphic, `DurationType` and `StatusCategory`; §7 gains the Forms-tab sharing chain and the fact that **Pre-Work Brief activation is `@ConnectHidden(from=Apex)`** and cannot be driven from Apex at all.

- **`dya-sf-cli` gains DevOps Center, org shapes and snapshots.** New `references/devops-center.md` documents the `sf devops` topic and, more usefully, the two async behaviours that make a failed promotion look green: `promote` returns the async id as `requestId` while `request status` echoes it back as `requestToken`, and **status reports how the request was processed rather than whether the operation worked** — a `*_SUCCESS` status with a non-null `errorDetails` means it failed. `references/org-and-auth.md` gains the shape and snapshot commands with the flag facts that are easy to assume wrong (`sf org create shape --target-org` is the org being shaped, not a Dev Hub; `sf org list shape` takes no `--target-org`; and `--source-org` on scratch creation wants the `00D…` org Id, not the `3SR…` shape record Id). It also picks up the scratch-org behaviours that change how a script is written: the command blocks so polling afterwards is wasted, a timeout is exit code 69, **a reused alias is silently re-pointed** rather than rejected, `target-dev-hub` is directory-scoped, and a Dev Hub can surface in any of the five buckets of `sf org list --json`.

- **`dya-integration-events` can now actually enable CDC, and stops telling readers to hand-roll replay tracking.** The skill described change events, Pub/Sub and replay semantics without naming a single metadata type, so an agent asked to "enable CDC on `Order__c`" had no correct path. Enabling it is `PlatformEventChannelMember` and nothing else — there is no `ChangeDataCapture` type, and a `.changeDataCapture-meta.xml` fails with "Could not infer a metadata type". §4 now carries the two naming rules that disagree with each other on purpose: `<selectedEntity>` is the ChangeEvent type with its double underscore (`Order__ChangeEvent`) while the **filename uses a single one**, because a double-underscore filename is parsed as a namespace and rejected. New `references/cdc-metadata.md` holds the element inventories (four elements exactly on the member, two on the channel, and `<label>` rather than `<masterLabel>`), custom `__chn` channels, the enrichment and filter constraints — including that compound fields take the flat name in one and the dotted name in the other — and the error-to-cause map. Separately, §7 told the reader to store the last processed replay id by hand; **`ManagedEventSubscription`** makes the platform hold that position, consumed through the Pub/Sub `ManagedSubscribe` RPC, which removes the commonest source of duplicate or skipped events. It comes with two facts that read like bugs: the API takes about two minutes to see a change, and `EARLIEST` on a busy channel replays the whole 72-hour window on activation — the abstract retention figure made concrete.

- **`dya-permissions` gains the metadata layer it never had, and a third axis.** The skill owned the access model conceptually and named **no metadata type at all** — not `objectPermissions`, not `sharingOwnerRules`, not one API name — which made it unactionable for anyone authoring rather than clicking. §3 now carries the OWD facts that change a design: the value set is not uniform (Case and Lead add `ReadWriteTransfer`, Campaign `FullAccess`, Price Book has its own model with external immutable at `None`), some objects are not configurable at all (User, Activity's external default, Knowledge), and setting **Account to Private drags Contact, Case and Opportunity with it** while Contract simply follows Account — so a one-object ticket is a four-object recalculation. Sharing rules gain the constraint that matters at design time rather than cleanup time: an owner-based rule allows only its access level to be edited, `sharedTo` / `sharedFrom` changes are a delete-and-recreate, and a normal deploy is additive so it will never remove a rule. `references/record-sharing.md` and `references/object-and-field-access.md` carry the XML — including that **a required field listed in `fieldPermissions` fails the deploy**, and that a `PermissionSetLicenseAssign` must precede the `PermissionSetAssignment` whenever the set carries a licence. Two new references open the regulated-data axis the skill did not cover: `data-privacy-and-encryption.md` (the four-value `encryptionScheme` enum and why only the deterministic ones can be filtered, the three key models, `DsarPolicy` — which is **export and never erasure** — and Data Mask, where a `LIMIT` is silently ignored and masks the whole table) and `dataspace-access.md` (`dataspaceScopes`, `BY_POLICY`, and the fact that `DataspaceScope` is not SOQL-queryable, so a query returning `INVALID_TYPE` is not a permissions problem).

- **`dya-apex`**: the Tony Scott trigger framework is now the default for greenfield orgs only (ask in existing orgs); added a per-object hierarchical trigger kill-switch (`Trigger_Settings__c`).
- **`dya-lwc`**: refreshed for Summer '26 / API v67.0 — `@lwc/state` State Manager (GA), grouped `<details>` accordions, `lightning/accApi`, `blob:` downloads (Lightning Web Security blocks `data:` URIs), Component Preview and SLDS Flow-screen hooks GA.
- **`dya-flow`**: documented the v67 `InvocableActionExtension` Apex Action configuration (per-input editors, picklist values, custom header) and the no-argument-constructor requirement for invocable action input types.
- **`README.md`**: the catalogue is now a grouped vertical list covering all 25 skills — the previous wide table went unreadable past a dozen entries and had fallen seven skills behind the repo. The layout diagram was redrawn around the actual tree, and the packaging section now points at the scripts instead of inlining shell snippets.
- **`.gitignore`**: stopped ignoring `.claude/` wholesale so repo-level skills and configuration are versioned (only `settings.local.json` stays local); added secret exclusions (`.env*`, `*.pem`, `*.key`, `*.p12`, `*.jks`, `credentials*`, `.sf/`, `.sfdx/`), which were absent from a public repo whose skills document OAuth, JWT and Named Credentials.
- **Repository renamed to `dyarchia-salesforce` and restructured as a Claude Code plugin.** The umbrella is now the GitHub organisation, not this repo: one repo per domain, one plugin per repo. `dyarchia-sf/` became `skills/` (one nesting level removed), the root `.skill` bundles moved to `dist/`, and `dyarchia-sf-sources/` became `sources/`. The packaging and validation scripts take `SourceRoot` and `OutputRoot` overrides, defaulting to the new paths.
- Made repository documentation provider-agnostic: removed vendor-specific branding
  in favour of neutral "agent skills" terminology, since the skill format is a
  cross-vendor standard.

### Removed

- **`dya-providers-tui`** — the cross-provider terminal-agent reference (Claude Code, Antigravity CLI, Grok Build, Mistral Vibe, opencode) and its five `references/` files. It is not a Salesforce domain skill and sits outside the scope of this library; its `.skill` bundle is no longer published. The skill was never part of a tagged release.

### Fixed

- **`dya-permissions` bundle rebuilt** — the published `dist/dya-permissions.skill` carried a copy of `SKILL.md` with CRLF line endings while the committed source is LF, so the two artifacts disagreed byte for byte. The bundle had been built from a working tree in which that one file had been rewritten with CRLF; a `.skill` is a binary archive, so those line endings were committed verbatim instead of being normalised the way `core.autocrlf=input` normalises the source blob. The mismatch was invisible in the working tree that produced it and failed `validate-skills` on every fresh clone. The bundle now matches the committed source and is byte-identical to one built from a clean checkout.
