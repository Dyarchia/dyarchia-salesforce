"Write selective queries" is a rule with actual numbers behind it. Without them the rule cannot be
applied, only recited.

## What selective means

The query optimizer inspects each filter in the `WHERE` clause and estimates how many rows it will
match. If at least one filter is backed by an index **and** matches fewer rows than the threshold for
that index type, the optimizer drives the query from that index. Otherwise it falls back to a full
table scan, which on a large object is slow and, past roughly 200,000 rows, throws `QUERY_TIMEOUT` or
the non-selective query error outright.

| Index type | Threshold on the first 1M records | Beyond the first 1M | Absolute cap |
|---|---|---|---|
| Standard index | 30% | 15% | 1,000,000 rows |
| Custom index | 10% | 5% | 333,333 rows |

A filter matching more rows than its threshold does not help, even though the field is indexed.
Selectivity is a property of the *filter*, not of the field.

## What is indexed

Indexed by the platform, no request needed:

- `Id`, `Name`, `OwnerId`, `CreatedDate`, `SystemModstamp`, `RecordTypeId`
- Every lookup and master-detail relationship field
- Any field marked **External ID**
- Any field marked **Unique**

Not indexed by default: ordinary custom fields, picklists, checkboxes, long text areas, and formula
fields (a formula field can be indexed only if it is deterministic).

A **custom index** on any other field must be requested from Salesforce Support — it is not a
checkbox in Setup. Design as if you will not get one, and treat it as an optimisation you may be
granted rather than one you may assume.

## What defeats an index

These constructs make the optimizer discard the index even on an indexed field:

| Construct | Why | Do instead |
|---|---|---|
| `!=` or `NOT` on the filter | Matches most rows by definition | Invert the logic to a positive `=` or `IN` |
| Leading wildcard: `LIKE '%acme'` | Cannot seek into a B-tree from the middle | Trailing wildcard `LIKE 'acme%'`, or SOSL |
| `OR` across fields where any branch is non-selective | The whole predicate degrades to the worst branch | Split into two queries and merge, or index both |
| Comparing an unindexed nullable field to `null` | Nulls are not reliably indexed | Filter on a positive marker field |
| Filtering on a non-deterministic formula field | Cannot be indexed | Persist the value in a real field via automation |

## Diagnosing

The Developer Console's **Query Plan** tool (Help › Preferences › Enable Query Plan) shows the
cardinality and the chosen leading operation for each candidate plan. A plan whose leading operation
is `TableScan` is the one to fix; cost below 1.0 means the optimizer will drive from an index.

## Skinny tables

For very large objects that are read constantly, Salesforce Support can create a **skinny table** — a
denormalised copy holding a chosen subset of fields, kept in sync automatically, that avoids the join
between the base and custom-field tables. Like custom indexes it is a Support request, not a Setup
option, and it is a last resort after filtering and archiving.

## Anti-Patterns

| Anti-Pattern | Correct Approach |
|---|---|
| Filtering only on an ordinary custom picklist on a large object | Add an indexed filter (`Id`, a lookup, `CreatedDate`) to narrow first |
| `LIKE '%term%'` for search | SOSL, which is built for text search |
| `WHERE Field__c != null` as the sole filter | Filter positively on an indexed field |
| Assuming a custom index exists because the field is filtered often | Confirm it; request one from Support if justified |
| A query that is fine at 10k rows and never revisited | Design against the object's projected volume, not today's |
